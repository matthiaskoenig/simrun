# Release notes for simrun 0.1.0

The first release of `simrun`, a runner of simulation workflows on a small k3s cluster with Argo Workflows and Kueue, for people and agents ([sbmlsim#440](https://github.com/matthiaskoenig/sbmlsim/issues/440)).

## Features

- **Workflows of tasks with ports.** A workflow is a YAML file of tasks of task types from plugins, whose inputs read the output ports (`out/<port>`) of other tasks; the settings of a task are validated with the settings model of its type, so a misspelled setting is an error. The built-in type `command` runs a command in an image of its own.
- **Split tasks on a ledger.** A task type with `count_units`, `compute_unit` and `merge` is split into units, which the workers of its pods claim from a ledger of atomic renames in the run store. A coordinator returns once the ledger is complete and computes the units of dead workers, extra workers spread over the idle servers (`fastest`, at most eight pods) or the task stays on one server (`single-server`), and the merge runs once every unit is done; the result does not depend on the number of pods.
- **Priorities, preemption and take-back.** The runs of the owner of the cluster and the owner's agents, of the other people and of their agents have three priorities, each a base and a lower extra priority of Kueue, so a run of a higher priority preempts the runs of lower ones and a new run takes back the extra workers of the running runs of its own priority. A node can be reserved for one run.
- **Learned resources.** The memory of a pod is learned from the anonymous memory of the cgroups of earlier runs of its task type, model and cost setting; a pod killed for memory is retried once with 1.5 times the memory per process, and `estimate` predicts the duration of a split task from the seconds of its units.
- **Snapshots and environments.** The client snapshots the working trees of the model and its libraries, uncommitted changes included, into the run store with their provenance; the service locks their third party dependencies with uv, builds the image of the environment with BuildKit only when the registry does not have it, and the pods install the read-only snapshots editable at their start.
- **The service, the command line and the MCP server.** A FastAPI service with bearer tokens of people and agents submits a run in the background and returns its id at once, follows the workflows with a stateless controller, keeps the logs of the pods and an index of the runs in SQLite beside the store; the command line `simrun` and the MCP server `simrun-mcp` of the agents submit, wait for, list, compare, cancel and clean up runs.
- **Cluster deployment.** `deploy/cluster` is the cluster as a kustomization (Kueue v0.20.5, Argo Workflows v4.1.6, the run store on NFS, Zot, BuildKit and the service), `deploy/k3d` the overlay of the integration tests on k3d, which verify the design on a real cluster. The same run exports as a CWL workflow for cwltool (the extra `cwl`).
